Orderbook Simulation
OrderbookSim is a C++ application simulating a financial market order book. It efficiently manages and matches buy and sell orders while calculating the Volume-Weighted Average Price (VWAP).

Benchmark and test results

Question: what does supporting several order types cost on the matching path of the std::map baseline, and does the book keep price-time priority?

The book measured is Orderbook as it is in this repository: per side a std::map<Price, std::list<OrderPtr>> (bids std::greater, asks std::less), an unordered_map from order id to order, and an unordered_map of per-price level data. The container was not changed. Every addOrder also writes to OrderDetailHistory (buy, sell and purchase history, a live-order map, and one neural-network training step per trade), because that is what addOrder does here; the numbers are for that path, not for a bare matching engine.

All raw output is in results/. Nothing below is estimated.

Reproduce

From the repository root:

cmake -S OrderbookSim -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j 8
ctest --test-dir build # 37 tests
OrderbookSim/bench/run.sh --reps 10 --seed 42 # benchmark, writes OrderbookSim/bench/results

Workload

Seeded std::mt19937_64 (seed 42) with std::uniform_* distributions. Those distributions are implementation-defined, so the same seed gives the same flow with libc++ but a different one with another standard library.

  • Prices are integer ticks around a fixed mid of 100,000. Passive orders are placed uniformly at mid ± [1, L] ticks, L = 50.
  • Prefill: 1,000 passive orders. Warm-up: 100,000 calls, replayed untimed before every timed pass. Measured: 1,000,000 calls per repetition.
  • Each call: 10% aggressive (Market, Fill-and-Kill, Fill-or-Kill or Good-Till-Cancel, equally likely; buy or sell equally likely; limit L ticks through the mid; quantity uniform 1–200); otherwise a passive add with probability 1000 / (1000 + resting orders), else a cancel of a uniformly chosen resting order. Passive orders are 90% Good-Till-Cancel and 10% Good-For-Day, quantity uniform 1–100. There are no modifies in the mix.
  • Calls are classified by outcome: add rested without trading, match_* traded at least once (by order type), reject_* was an aggressive order that did not trade, cancel.

Realised (from results/main/workload.csv): 549,002 adds (54.9%), 350,996 cancels (35.1%), 100,002 matches (25,059 Good-Till-Cancel, 24,821 Fill-and-Kill, 25,147 Fill-or-Kill, 24,975 Market), 0 rejects; 2.95–2.96 trades per match. Resting orders: mean 640, min 537, max 772. Price levels: mean 37.9 bid and 38.0 ask.

Controls

  • Timer: std::chrono::steady_clock. Measured resolution on this machine is 41.67 ns (reported as 41 or 42 ns); back-to-back reads take 0 ns at p50 (same tick) and 42 ns at p99. Per-call latencies are therefore quantised in ~42 ns steps and are not overhead-corrected.
  • Allocations: the benchmark binary replaces global operator new/delete and counts calls and requested bytes inside each timed call. Allocations made with C malloc inside libc (for example in localtime_r) are not counted.
  • Pinning: macOS has no thread-affinity API. The thread runs at QOS_CLASS_USER_INTERACTIVE so the scheduler prefers performance cores; which core ran was not verified.
  • Repetitions: 10, each on a fresh book, replaying the identical call sequence. Every replayed call is checked to produce the same number of trades as the generation pass.
  • Throughput is a separate pass per repetition: the measured block timed as a whole, no per-call timer.
  • Not controlled: other processes, CPU frequency and thermal state.

Findings:

  1. Order types cost little on the matching path. Matches by Good-Till-Cancel, Fill-and-Kill, Fill-or-Kill and Market have the same p50 to within one timer tick (1,667–1,708 ns in main). Fill-or-Kill's pre-check, which walks the whole level-data map for both sides, adds one tick at p50; at p99 it adds 41–63 ns in main and 104–188 ns at 340 levels per side (levels500).
  2. **std::map is not the limiter.** Red-black-tree work is 1.2% of book time. Of the 45.5% spent in MatchOrders, 32.8 points are history and neural-network bookkeeping called from it (updateNeutralNetwork 26.8, removeMatchedOrder 3.5, addOrderToPurchaseHistory 2.5). The neural-network update includes localtime_r for a time-of-day input that static_cast<int>(fraction) * 100 always truncates to 0. Hash-map operations on all paths are 30.2%.
  3. Allocations. 5.49 per add, about 20.8 per match (about 7 per trade), 0 per cancel. About 20.9 KB is requested on every add and match because MatchOrders reserves room for _orders.size() trades (32 bytes each) on every call, traded or not; that cost scales with resting orders (4.5 KB at 130 resting orders, 204 KB at 6,376).
  4. The maximum is history growth. In all 40 repetitions of the four runs the slowest add (8.6–18.7 ms) requested 3.30–3.50 MB, of which 3,292,216 bytes is a rehash of the live-order unordered_map to 411,527 buckets and the rest the per-call trade reservation (slowest_call_bytes in latency_per_rep.csv; sizes identified in results/large_allocations.txt). Cancelled orders never leave that map, so it grows with every order ever added. In main the slowest Market match in 9 of 10 repetitions requested 8,409,436 bytes: the purchase-history vector doubling to 2^19 entries.
  5. Depth. From 8.6 to 38 to 340 levels per side, add p50 goes 167 → 208 → 375 ns, cancel 83 → 125 → 292 ns, match 1.54 → 1.67 → 1.96 µs and throughput 3.09 → 2.60 → 1.79 M calls/s. These runs do not separate std::map depth from the per-call reservation in finding 3 and the larger working set of the hash maps.

Not measured here

  • Other hardware, Linux, GCC or MSVC; an isolated machine; hardware performance counters.
  • Modify latency (no modifies in the benchmark mix); concurrent callers.
  • Memory per resting order: only process peak RSS, which includes the benchmark's buffers.
  • A latency or memory budget: the project states none, so there is nothing to compare against.
  • The original jideoyelayo1/orderbook repository: its bid/ask ordering is reversed, so its timings would describe a book that matches the wrong orders.
